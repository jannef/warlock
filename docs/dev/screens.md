# Screens, input, and key commands

Developer notes for working on this part of Warlock (moved from CLAUDE.md, #185); the
rules it implements are in spec/06-input-and-ui.md. Keep it current with the code, as CLAUDE.md says.

Modal screens (spec §6) — main menu, the saved characters (Characters), new run and character
creation (race, gender, class, talents, name, summary), pause, settings, controls, the `?` help, the inventory (`I`), the equipment screen
(`i`) and its choice of what goes in a slot, an item's description (a letter in the inventory,
an upper-case slot letter on the equipment screen), the character screen (`@`), the weapon skills
screen (`W`), the quest log (`q`), the message history (`v`), choosing what to
pick up (`,`/`;` on several stacks), drop (`d`: the inventory in its drop mode), eat (`e`), or read (`r`; then, for the scroll of
identify, what to read it on, `ScreenName::Identify`, which takes the read list's place), the
Decipher ability's list (`ScreenName::Decipher`, `ObjectList::Decipher`: the scrolls carried of a type
not yet identified, `world::undeciphered`; choosing one sends `Action::Decipher`), the
abilities menu (`a`), the
dialogue screen (opened by
`screens::show_identified` opens the description screen (`DescribeScreen`) for the stack
a cast of Identify (a cast or the scroll of identify) just told something of, from `Event::Identified { item }`
(only when no screen is open; Esc returns to the map); `screens::converse` after an action this frame whose outcome is talk with topics,
`Event::Talked`; asking is `ScreenAction::Act(Action::Ask)`, which closes it, and the answer
reopens it on the topic asked, also when no topics are left), and the death screen (opened by
`screens::on_death` when `World::death` is set; Enter/Esc is `MenuChoice::LeaveRun`, back to the
main menu without saving; no `--screen`: capture a dead replay instead), the level-up screen (opened by
`screens::on_level_up` whenever `World::due` is set and the game changed, over whatever is open, the
death screen winning; its choices are `ScreenAction::Act`, which closes it, and it opens again on
what is left; no `--screen`: a replay that ends with choices due opens it), the Talents page
(page 8, `KeyCommand::Talents`, `G`), the Magic page (page 6, `ui/magic_screen.rs`, below), and the story screen (`ScreenName::Story`,
`ui/story_screen.rs`, below) — are one
screen stack (`ui/screens.rs`, the `ScreenStack` resource); add a screen there, never a second way
to open, read keys for, or draw one:
- **Dispatch** (#1542): every screen implements `ui/modal.rs`'s `ModalScreen` (`name`, `fit`
  before a press, `handle`, `draw`; most by one `modal!` line there), and the stack reaches it
  through `Screen::modal`/`modal_mut`, generated by `screens.rs`'s `dispatch!` from the one list
  of `Screen` variants. A press reaches the screen as `modal::Keys` (the settings and bindings it
  may change), drawing reads `modal::Show` (settings, bindings, clock, the menu's notice). A new
  screen is a `ScreenName` value, a `Screen` variant with its `dispatch!` line and `Screen::new`
  arm, and its impl. `ScreenName::needs_run` lists the screens that do *not* need a run.
- **Item lists** (#1542, #1547): `ui/object_screen.rs`'s `ObjectList::spec` is the table, one
  `ListSpec` per list (its `ScreenName`, title, empty words, rows, footer verb, and the action
  a chosen stack makes when that is all it does); `Screen::new` opens a list by its name
  (`ObjectList::of_screen`, the `BY_NAME` lists) and `Screen::name` asks the screen. Which
  stacks a list offers is core's: `warlock_core::item_list::ItemList` and
  `PerceptionView::item_choices`/`floor_choices` (the rules' own predicates, `world::workable`,
  `salvageable`, ...). An ability that asks for a stack names its list (`Aim::Item(ItemList)`),
  and `use_ability` opens `ObjectList::screen_of(list)` (the identify list opens for the
  ability used, `identify_by`). A new item ability is an `ItemList` variant with its arm in
  `item_list.rs`, its `Aim`, a `ScreenName` value, and an `ObjectList` entry.
- **Open**: `Screens::open(ScreenName)` (a `SystemParam` over the stack, content, save store, and
  the run, if any) is the one way a screen opens: `?`, `I`, `i`, `@`, `W`, `,`, `d`, and Esc in play,
  sub-screens, the startup main menu and `--screen`, and the return to the main menu after a run.
  Screens that show the run read the perception snapshot when they open (no time passes while
  they are open but for an action chosen on one). Back/Esc pops the top screen, so a sub-screen
  returns to the screen it was opened from as it was left; `ScreenAction::Return(name)` pops
  until `name` is on top (the summary going back to a step). Sub-screens read what was chosen
  below them off the stack: character creation's steps (`ScreenStack::draft`: New run's scenario
  and seed, each step's selection) preselect what was chosen before going back
  (`ScreenStack::picks`), else the scenario's character (the name step: what was typed, else an
  empty field), and the summary's Start is `MenuChoice::NewRun { scenario, seed, character, name
  }` with the seed `ScenarioPick::seed` resolved (#256): New run's seed field exists only where
  `input::dev_keys` is true (debug builds, `--dev`; `Launch::dev`), empty meaning the scenario's;
  elsewhere `Screen::new` hands `NewRunScreen::new` a `new_run_screen::fresh_seed()` (the
  platform clock and entropy, the app's, never core's) and no text mentions it
  (`ScenarioPick::shows_seed` gates the summary's `, seed N`); a New run with one scenario (a
  release build) is skipped: `Screens::open_on` opens the race over it at once, and
  `ScreenStack::close` takes it off with the race (`NewRunScreen::skips`,
  `docs/dev/campaign.md`); the main menu and the Characters screen read the saved characters when they open
  (`Launch::characters`, from `SaveStore::characters`; no other screen lists the saves);
  `EquipItem` takes the slot selected on the
  equipment screen beneath (`ScreenStack::selected_slot`), and `Describe` the stack looked at
  on the inventory or equipment screen beneath (`ScreenStack::looked_item`; the first stack
  without one, as `--screen describe` opens it over the inventory).
- **Input**: `input::route_keys` is the one reader of `KeyboardInput`. Stack not empty: the press
  goes to the top screen as a `Press` whose `nav` comes from the fixed menu keys
  (`settings::fixed::menu`, #1533) and `Back`'s bindings (Esc is always `Nav::Back`; see
  `docs/dev/settings.md`: a screen never matches a key code or a character, except list letters
  and digits and the typed seed; a numpad key nothing else claims is the arrows' fixed alias there,
  `menu::numpad_nav`: 8, 2, 4, 6 are Up, Down, Left, Right, and NumEnter is a fixed Enter, #1197)
  and whose `edit` comes from the fixed text keys (`settings::fixed::text`) and `TextBack`'s
  bindings (Esc is always `Edit::Back`), for the text field, which reads only
  `edit` and `text` (the key event's text, literal; else the character its key stands for), so
  every other key types; held keys type and erase but never accept
  (`ScreenStack::handle` →
  `ScreenAction`: stay, close, open, a
  `MenuChoice`, or `Act(Action)`: close and apply a gameplay action, e.g. `pickup:ac`,
  `equip:body:b`; the screens beneath stay, and `screens::refresh`, after `SimSet`, shows the
  equipment screen the result, as in ADOM, and reads every open object list again
  (`ObjectScreen::refresh`: the read list stays beneath the dialog that reads a grimoire, and a
  scroll used up moves the stacks after it, so a row kept from before would name another stack,
  #591));
  otherwise
  it is a gameplay command in the current `InputMode`. Opens and closes apply at once, so the next
  press in the same frame goes to the new top; menu choices (start, resume, save-and-quit to menu,
  quit) are messages applied by `screens::apply_choice`, and the rest of that frame's presses are
  dropped, as they are after a screen's `Act` while an object list stays open
  (`ScreenStack::shows_objects`: the list is read again only once the action is applied; tests
  `ui/stale_list_tests.rs`). Held-key repeats never open, close, choose, or act.
- **Draw**: `ui::draw` is the one system that writes the UI console: when anything it shows
  changed, it clears the console, draws the gameplay UI if a run exists, then the top screen.
  Footers name the menu keys as bound (`ui::menu::Hints`: `↑↓` and Enter with the defaults).
- **Dialog** (`ui/dialog_screen.rs`): the one question screen; **every** confirmation is this
  screen with its own parameters, never a screen or prompt of its own. A screen or gameplay
  answers `ScreenAction::Dialog(Box<Dialog>)` (`Dialog` converts `into()` it; `Screens::ask`
  opens it). A `Dialog` is a `title` (on the frame), the question `text` (wrapped), and
  `options`: each a `Choice` with a `label`, a `Role` (`Accept`, `Decline`, `Cancel`, `Plain`),
  and an `outcome`, any `ScreenAction` (`From<MenuChoice>` is `Choose`, `From<Action>` is `Act`,
  a `Dialog` is a follow-up that takes its place, `Close`). Build it with `Dialog::new(title,
  text).accept(..).decline(..).cancel(..).plain(..)`, or `Dialog::yes_no(title, text, yes,
  outcome, no)` for a plain question. It sizes itself to its content and draws the options in
  a column, each with its shortcut keys. Keys: the menu keys move the selection, Enter takes it;
  the fixed `y` and `n` (`settings::fixed::dialog`, #1533) pick the Accept option and the Decline
  option (else Cancel); Esc picks Cancel (else Decline; else closes), except in a dialog that must
  be answered (`Dialog::required`), where Esc does nothing; the safe option (Cancel,
  else Decline) is selected first. A menu choice pops the dialog and is applied as usual, an
  action closes it and is applied (`play.act`, which may answer with a dialog of its own: the
  sell offer), a follow-up dialog replaces it (`ScreenStack::handle`). Users: every quit path
  (`menu::quit_dialog(saving)` for the pause and main menu Quit and a bound `KeyCommand::Quit`,
  `save_to_menu_dialog`), the step into deep water (`ui::step_dialogs::deep_water_dialog`, spec §8 "Skills": Swim; first in the step's chain, below), the step onto a known trap (`ui::step_dialogs::trap_dialog`, spec §8 "Traps"), an overworld step while Fainting or Starving (`ui::step_dialogs::hunger_dialog`, spec §8 "Hunger"), a step into a feature that offers an action (`ui::step_dialogs::offer_dialog`, `docs/dev/special-rooms.md`), a burst
  read so close it may catch the player (`ui::step_dialogs::burst_dialog`, spec §8 "Scrolls"), the shop (`ui/step_dialogs.rs`: `leaving_dialog`, `sale_dialog`; spec §7 "Shops"), and the overworld
  encounter (`ui/encounter.rs`: `on_encounter`, after `on_death` and before `on_level_up`, opens
  `dialog(view)` from `PerceptionView::encounter()` whenever the run changed with one pending and
  none is open, so after the step and on load; a plain row per choice, `Action::Encounter`;
  `required`: no Esc, no info page over it, the owner's #796 Q9; `docs/dev/encounters.md`). **A new
  question is a `Dialog` value at its call site**, e.g. `Dialog::yes_no("Quest", text,
  "Accept", Action::.., "Not now")` returned as `ScreenAction::Dialog`, with no screen, prompt,
  `InputMode`, or key handling of its own (quests are given through dialogue topics, which
  are no question).
  `--screen dialog` shows the quit dialog. On wasm, quit saves then reloads the page
  (`storage::web::reload`; `AppExit` also reloads), and the main menu has no Quit.
- **Info pages** (`ui/info_tabs.rs`): the screens about the player (Character, Inventory,
  Equipment, Skills, Weapon skills, Magic, Quests, Talents, Story) are an ordered group, `PAGES`, each with its name and
  a short name for the tab line ("Inv"; the short line fits an 80-column console). Every page's panel is at least `info_tabs::panel_width`
  wide (111 cells, sized to the tab line by every name, `1 Character · … · 9 Story`; clamped
  to the console like any panel), so the pages share one frame and the tab line stays put as
  they turn: only its highlight moves. The tab line takes the first of these that fits, the same
  form on every page: every name; every short name; bare keys. The keys shown are the page keys
  as they are bound. While one is the top screen, the page keys replace
  it (`ScreenAction::Replace` -> `Screens::replace`: the stack depth is unchanged, so Esc still
  returns to where the first was opened) and each draws its tab line on the bottom border with
  `info_tabs::draw_tabs`. **A new info screen joins the group**: one entry in `PAGES` (its
  position is its number), its panel sized with `panel_width`, and one `draw_tabs` call in its
  `draw`; never a separate way to switch.
  Sub-steps of a page (`EquipItem`, pick-up/drop/throw lists) are not pages and keep their
  number keys. The keys are fixed (`settings::fixed::page`, #1533): the top-row digits `1` to `9`
  and Tab (Shift reverses), with `PrevPage` (`Context::Pages`, unbound) the one rebindable
  back-style command. `Press::shift` carries Shift from the router. The dialogue screen
  is no page: its digits ask about topics, the top row's only (`Press::is_numpad`).
  **The numpad on screens** (#1197): it is navigation, never page switching, matched by
  physical key (`KeyCode::NumpadN`) whatever Num Lock says. winit 0.30 reports a numpad key with
  Num Lock on as `Key::Character("8")` with the text `8` (macOS, which has no Num Lock, always),
  and with it off as `Key::ArrowUp`, `Home`, `PageUp`, and so on, with no text (Windows,
  X11/Wayland). Page keys and dialog shortcuts are matched by `Press::binding`, which is
  `KeyBinding::Code(NumpadN)` for a numpad key either way, so a numpad digit never turns a page
  or answers; a text field types the digit's text (Num Lock on). The look and aiming cursors
  read play's `Move` bindings, so they take all eight numpad directions.
- **The Magic page** (`ui/magic_screen.rs`, `MagicScreen`, `ScreenName::Magic`, `--screen
  magic`; spec §6 "Magic"; the spell scaling design §11): page 6, no `KeyCommand` of its own
  (reached by its number or Tab; the weapon skills screen's footer names it with
  `info_tabs::hint`). One column of rows built once when it opens (`rows`): `Mana a/b`, the
  caster styles (the styles whose `Grip::casts`; only for a player who
  knows a spell or has a rank or marks in one), and the spells, filtered from
  `PerceptionView::abilities` in its order, each with its rank (`PerceptionView::own_spell_rank`,
  `rank 3` in a column of `RANK_W`; spec §8 "Spells": "Ranks", #1264) and
  `abilities_screen::spell_head` (the menu's row,
  "2d4 force, 4 mana", plus ", aimed" where `needs(aim)` says anything). Scrolls as the weapon
  skills screen does (gaps give way, then ↑↓, `most` stored at draw). The weapon skills screen
  leaves the caster styles out. Snapshots `magic-screen` (the showcase wizard at level 1),
  `-trained` (level 18, `rank:sniper:5 rank:toucher:3`), `-armoured` (a paladin in the
  forge's chain mail: Battle caster marked), `-none` (a warrior), `-short` (80 × 20: the scroll).
- **The story** (`ui/story_screen.rs`, `StoryScreen`, `ScreenName::Story`; spec §6 "Your story",
  #703; `docs/dev/background.md` "Shown"): the paragraphs of `PerceptionView::story`, wrapped,
  scrolled a line by `Nav::Up`/`Down` when the console is short (the stack calls its `fit` before
  a press, the message history's way); Enter and Esc close it. Two looks of one screen:
  `StoryScreen::opening` (72 wide, `Enter continue`, no tab line; `is_opening`, which the stack's
  page switch skips, so the digits do not turn it) and `StoryScreen::page`, page 9 (the pages'
  width and tab line; "Your story is not written." without a story). `Screens::open(Story)` (a
  page key) opens the page; `Screens::open_story` the opening, from two places only:
  `open_startup_screens` for `--screen story`, and `screens::on_run_start` (in the run's
  screen chain before `converse`), which opens it when `Game` was just added
  (`Res::is_added`), `Game::story_due` is set, the stack is empty, no death, and the story is not
  empty. `Game::story_due` is set by `Game::new_run` (the summary's Start) and by `Game::start`'s
  fresh-run branch without `--capture`; never by `from_world` (Continue, Resume), a replay, or a
  resume. Nothing is saved: a run resumed on turn 0 reads it on page 9. Snapshots
  `story-screen` (the summary's Enter: the real opening), `story-page` (112 wide: the full tab
  line), `story-page-none`; the opening rule's tests are in `ui/screens.rs` and `game.rs`.
- **Item lists** (`ui/paged_list.rs`, spec §6 "Item lists", #188, #189): **every lettered list
  of stacks is the one `PagedList`** (the inventory, pick up, drop, throw, eat, read, identify, the
  equip choice;
  sell is a drop in a shop, identify a dev action): never a list or scrolling of its own. The
  abilities menu is one too, grouped by `Source` instead of item class (it keeps the top and bottom console rows free for the message line and status bar, #1369)
  (`PagedList::grouped(items, name)`; `PagedList::new` groups by item class). A stack's row
  names it with `Lore::listed` (its name and its numbers, `(+0 hit, 1d8)`, `(Dv +1, Pv 1)`;
  `magic::numbers`, #552), so the item lists' panels are 78 wide (the equip choice's too). Items
  group by item class in class order (`PerceptionView::item_class`), a header row per class
  (`Row::Header`, no letter), each class in the items' own order. A page holds as many rows as
  the console has for it (the screen's `fit`/`layout`, which sets `PagedList::set_room`;
  where room, not the 26 letters, is what pages the list, the screen's margin and gaps give way
  first) and at most 26 items; letters run down a page from `a` and restart on every page
  (`at_letter`), a class split across pages repeats its header, and the frame shows `Page 2/3`
  (`draw_label`). The list's cursor picks the page shown; Up/Down move it across pages (wrapping
  round at the ends, `ui/cursor.rs`, the step every screen's list takes), and the
  fixed menu keys `>` (PageDown) and `<` (PageUp), `Nav::NextPage`/`PrevPage`, turn the page (cursor to its first item; no wrapping). Drawing knows
  the console, presses do not: `route_keys` keeps `ScreenStack::console` current and the stack
  calls the screen's `fit` before each press, so a letter names what is drawn even before the
  first draw (`--keys`). Screens hold stack positions (`Item::position`), never letters, and
  send actions by position.
- Prompts in the message line (open/close/bash/chat direction, rest, look mode, aiming,
  `--more--`) are `InputMode`s, not screens (`Gameplay::press` hands a press to its mode's
  handler: `input/play.rs` in plain play, `input/prompts.rs` for the prompts; look mode's second row starts with what Knowledge
  tells of the creature under the cursor, `look::known`, its hint after it: the hint clips first,
  docs/dev/skills.md); a question (the step onto a known trap,
  `ui::step_dialogs::trap_dialog`; a journey while Fainting or Starving, `ui::step_dialogs::hunger_dialog`; a walk into what offers an action,
  `ui::step_dialogs::offer_dialog`) is the dialog (above). A step opens one dialog, the first that applies:
  deep water, leaving a shop owing, a known trap, a journey while hungry, an offer. Deep water
  comes first, as it always asks and any other answer would step in unasked; its "Dive in" is a
  plain move, so the keeper still turns back one who owes, and a trap under it would still go off.
  The hungry journey (overworld, walkable) and the offer cannot apply to a step into deep water.
  With no dialog, a walk into an anvil opens a screen instead (`ui::step_dialogs::step_screen`, #1387):
  Metalcraft's profession screen for one with its row, at once and with no time; untrained, the
  step goes to the rules, which say what it needs.
- **The message line and `--more--`** (`ui/more.rs`, spec §6 "Messages", #207): `Game::read` is
  the message log as it was when the player last acted (`Game::apply` takes it before applying;
  a new run starts with nothing read, so its welcome is news; `Game::from_world`, a resumed run,
  has read everything; a replay's last step is news, `play_replay`; a loaded snapshot calls
  `Game::mark_read`), and `Game::unread` lines it up with the log (which only grows at its end,
  folds repeats into its last entry, and drops its oldest beyond `messages::CAPACITY`) to give
  this turn's messages. `more::pages` runs them on in rows of the console's width less a margin
  either side, split at word boundaries, in pages of `MESSAGE_ROWS`, every page but the last
  leaving room for ` --more--`. `more::wait` (after `SimSet`, before `draw`) enters
  `InputMode::More(0)` when a new action (`Game::applied`, or a new run) needs more than one
  page, or left the player hungrier (`Game::hunger_stop`: the last page waits too, and `more::pages`
  leaves it room, docs/dev/hunger.md), from play only (a dev flag's aiming or look mode keeps its
  mode), and follows a resize.
  In `More(page)` `Gameplay::press` (`input/prompts.rs::more`) reads `Context::More` first: `MoreNext` (Space, Enter)
  turns to `more::advance(page, more::stops(..))` (play once none is left to wait at), `MoreSkip` (unbound)
  and Esc go to play; every other command, and every held key's repeat, does nothing. Screens
  keep their keys while it waits beneath them. `more::draw` draws the page waited at with
  `--more--` after it, else the end of this turn's messages with earlier ones, one a row, in the
  rows left. Presentation only: dumps and replays never see pages. The rules never ask: a `move` steps onto whatever is there.
- **Something beside the player** (#1327, `warlock_core::beside`): `Beside` names what acts on
  a cell beside the player (`Open`, `Close`, `Chat`, `Dig`, `Use(ability)` for an ability aimed
  in a direction); `Beside::target` its `Target` (a closed door, a known trap, a foe, ...), and
  `PerceptionView::ways` the ways to the legal ones, from the perception only.
  `PerceptionView::way` turns them into `Way::Refuse(dir)` (none: `blank_way`, the first known
  wall, no door or chest, else north, so nobody unseen is struck), `Way::Act(dir)`, or
  `Way::Ask`. `Gameplay::beside` is the one input helper: `o`, `c`, `C`, `u` with a digging tool,
  and `Gameplay::use_ability`'s `Aim::Direction` arm go through it (Kick never: it always asks).
  `PerceptionView::abilities` reads the same ways: a direction ability otherwise usable but with
  none is `Unavailable::NoTarget(target)` ("no lock beside you", `no_target:lock`), and Listen
  and Wedge are left out without one (the owner). An unavailable ability is applied toward
  `blank_way` too. Heal's and Give's ways between two kept beasts stay their own (`tend_way`,
  `InputMode::GiveWay`).

**Abilities** (spec §6 "Abilities"; racial, class, skill, weapon skill and style, item; the
owner's rule, #156) get no key of their own: they go into the one abilities menu.
- **Registry**: `warlock_core::ability` is the one place they are registered. A new ability is
  a variant of `Ability` (id, name, description, `Source`, `Aim`, cost `ActionKind`, the `Action`
  it makes from its aim), a line in `Ability::every` (menu order: by source, then as listed),
  who has it (`had_by`), and when it cannot be used (`unavailable` → `Unavailable` with its
  reason; `While(status)` for a status that blocks its cost's kind or is its cooldown,
  `docs/dev/status-effects.md`; alignment never makes one unavailable, `docs/dev/alignment.md`;
  `reason`/`id` take the content). `PerceptionView::abilities` is what presentation reads (`OwnAbility`: the ability and
  why it cannot be used now); the `abilities` dump layer and JSON key show the same, and the
  wiki's table (`xtask/src/wiki/abilities.rs`) lists `Ability::every`. The orders to one's allies
  (`Ability::Heel`, `Hold`, `SetOn`, `Source::Ally`, the Allies group after Here) are had by nobody
  and listed by `Ability::orders` while the player has an ally anywhere, greyed `NoAllies` with
  none on the level (docs/dev/allies.md). Skills used as actions are
  `Ability::Skill(id)` until their use exists (never available); a use, when it comes, is a
  variant of its own, listed in its skill's place (`Ability::use_of`: the skill's benefit effect
  names it, so `had_by` asks `Skills::trains_effect`): `Ability::Disarm`, Disable device's
  (`docs/dev/traps.md`), `Ability::PickLock`, Open lock's (`docs/dev/doors.md`), and
  `Ability::Steal`, the `steal` benefit's (`docs/dev/stealing.md`), `Ability::Feint`, the `feint`
  benefit's, in a direction, and `Ability::Intimidate`, the `intimidate` benefit's, aimed at a cell
  (`docs/dev/skills.md`).
  `Ability::SecondWind` (`Source::Talent`, the menu's Talents group between Class and Skills) is
  the first active talent's (`docs/dev/progression.md`): listed while the content has a talent
  with the `second_wind` effect, had by whoever holds one, `While(winded)` during its cooldown.
  `Ability::BloodMagic` (`Source::Talent`, after it) is Blood magic's (`docs/dev/mana.md`):
  listed while some talent has the `blood_magic` effect, had by its holders, never greyed out
  (the rules refuse low hit points and full mana).
  `Ability::Sign(SignActive)` (`Source::Sign`, the menu's Birth sign group between Racial and
  Class) are the birth sign's actives (`docs/dev/character-creation.md`): listed while some talent
  has one, had by whoever's `TalentMods` has it, `While(cooldown)`; their action is
  `Action::Gift` (`use:horns_grace`, `use:transfixing_stare:X,Y`, a cell at `STARE_RANGE`).
  `Ability::Class(ClassActive)` (`Source::Class`) are the class actives
  (`docs/dev/progression.md` "Class actives"): listed while some talent has one, had
  by whoever's `TalentMods` has it, `While(cooldown)`; their action is
  `Action::Use`. No `KeyCommand` of their own (as Second wind's).
  `Ability::Sign(SignActive)` (`Source::Sign`, the menu's Birth sign group between Racial and
  Class) are a birth sign's actives (Blaze; `docs/dev/character-creation.md`): listed while some
  talent has one, had by whoever's sign grants it, `While(cooldown)`; their action is
  `Action::Gift`.
  `Aim` has `Nothing`, `Direction`, and `Cell` (aimed in the targeting
  mode, `ui/target.rs`'s `AimKind::Ability`: no line of fire, `Line::unseen` for a cell not seen
  or solid, the reach from `Ability::reach` (a caster's spell's from its data, every other's
  `Ability::range`), the action from `Ability::action_at`; a caster's strike, `Ability::Spell`,
  is aimed as a spell scroll is: its arm in `ui/target.rs` (`AimKind::Ability(Ability::Spell(_))`)
  gives it the scroll's line of fire, and `ui/step_dialogs.rs::burst_dialog` asks "Cast it anyway?" when its burst may catch the player); an item (a
  `PagedList` of the pack) joins them with the first ability that needs one, as a variant and an
  arm in `Gameplay::use_ability`. Throwing one's voice (`Ability::ThrowVoice`, Class) is had
  by those a talent gives it. A lantern is no ability: `u` (`KeyCommand::UseTool`) turns a
  light ready in the Tool slot (`PerceptionView::ready_light`) at once, `Action::UseTool`, and
  digs otherwise (#643), by the rule for something beside the player (above).
- **Menu**: `ui/abilities_screen.rs` (`AbilitiesScreen`, `ScreenName::Abilities`, `--screen
  abilities`): the `PagedList<Entry, Source>`, greyed rows with their reason (an active weapon
  ability's after its stamina, `PerceptionView::own_weapon_stamina`: "3 stamina, in a
  direction", "4 stamina: you are short of breath"; never its time; snapshots
  `abilities-menu-weapon-actives`, `-short`; a spell's detail column is its roll now with its
  type, its mana, and "aimed", `4d6 fire, 26 mana, aimed`, short of mana `: you have 14`,
  `PerceptionView::own_spell_roll`, snapshots `abilities-menu-spells`, `-grown`), the selected
  ability's description below (three lines; a spell's adds its reach and a reroll, "Range 11,
  radius 2. Your 1s are rolled again."); the stack calls its `fit` before a press like the item lists. A
  letter or Enter on an available row answers `ScreenAction::UseAbility(ability)`; on an
  unavailable one it shows why and stays. Its own key closes it only when it names no row.
- **Dispatch**: `ScreenAction::UseAbility` is the one way an ability is used, from the menu, its
  own key (`KeyCommand::Bash`, `Disarm`, `PickLock`, `ThrowVoice` answer it from
  `Gameplay::press`), or the quick repeat:
  `input::route_keys` closes the top screen if any, remembers it (`ScreenStack::last_ability`,
  cleared with the stack when a run ends, like the creation picks), and calls
  `Gameplay::use_ability`: `Aim::Direction` goes through `Gameplay::beside` (above): with
  several targets it enters `InputMode::Ability(ability)` (the message
  line's "In which direction? (Esc to cancel)", disarming's "Disarm in which direction?",
  `ui/mod.rs`; a direction applies `ability.action(Some(dir))`),
  `Aim::Cell` starts aiming (`InputMode::Aim`, `AimKind::Ability`), `Aim::Nothing` applies it
  at once, and one that cannot be used now is applied at once toward `PerceptionView::blank_way`
  (or the player's own cell) so the rules say why and take no time (as `u` does with no tool).
- **Quick repeat**: the menu opens on `ScreenStack::last_ability` (else the first available row);
  `X` (`RepeatAbility`, passed the last ability by `route_keys`) answers `UseAbility(last)`, or
  opens the menu when there is none.
- **Keys**: an ability with an action of its own may have a rebindable `KeyCommand`, left unbound
  by default (`settings/keys.rs::UNBOUND`); never a default key. Shield bash is the first, Steal
  the second; a style's rank 10 abilities (later) go there too. They stay (the owner, #644), and
  `settings/keys.rs::ABILITY_KEYS` lists them: Controls and the `?` help show them last, below
  every context's group, under "Ability keys" (`controls_screen::Row::AbilityKeys`; text
  snapshot `controls-screen-bottom`).

**Text snapshots** (#301): `ui/screen_snapshots.rs` (test only) checks the screens as text, in
place of golden screenshots. Each `Case` starts a run the way a golden entry does (scenario,
`character`, `kit`, action text, `screen` as `--screen`, `keys` as `--keys`, `save_dir`, the
console `size`). It runs the real systems headlessly (`open_startup_screens`, `route_keys`,
`apply_choice`, `refresh`, `converse`, `on_death`, `more::wait`, `draw`) and snapshots the UI
console with `insta` (`ui/snapshots/`, one file per case). The map layer and colors aren't part
of it: map content is `warlock-cli dump`. To add one, add a case under its group in `cases!`
(`test_name: Case { name: "test-name", .. }`: one `#[test]` a case, #1529, so one mismatch
hides no other), run `cargo test -p warlock screen_snapshots`, then `cargo insta review` (or
`INSTA_UPDATE=always`, then read the diff). The snapshot leaves out the status bar's row where
it shows whole (`shown`, #1521: a HUD change rewrites only the cases about the bar, those with
`status_bar: true`) and writes the game's version `[version]` (#1532). A changed screen shows as a text diff in the PR. New
screens get a case here, never a golden (CLAUDE.md "Golden screenshots").
